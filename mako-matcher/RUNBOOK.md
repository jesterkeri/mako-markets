### 6.5 Operator key: revocation and rotation runbook [r3]

Lives here, and is copied into the Worker package as `mako-matcher/RUNBOOK.md` in slice 2 (§10.1). Rehearsed once on testnet in slice 5.

**Who.** Joshua holds the exchange admin key and runs every command that signs, as in S0 and S1. Claude prepares the exact commands and checks each result read-only.

**The key.** Worker secret `OPERATOR_PRIVATE_KEY`; Bitwarden item `mako-matcher-operator-key`; pushed with `mako-design/scripts/bw-secret-to-worker.sh`, never displayed. Funded with gas MON only, **[r14]** and only under the daily top-up rule of §6.3: at most one top-up per UTC day, and the balance after it at most `C` (r3's "at most two days of the settler's daily MON cap" is withdrawn). It holds no USDC and no shares.

**[r14] Top-up.** **[r27]** When the helper reports the keys low, at most once per UTC day: run `node mako-matcher/scripts/topup.mjs` (§6.3). It prints either a refusal (a top-up already made this UTC day, the keys at or above `C`, the contract short of the amount, a failed reconciliation, no recipient, or an unreadable send log; **[r27]** a revoked key's `retireKey` is printed in place of the call, and the helper is run again once it mines) or the exact call `topUp(R, A, D)` on the funder contract; sent after day `D` it reverts `WrongDay`, and the helper is run again. Joshua sends it from his owner wallet. Claude checks the transaction, its `TopUp` event and the balances after, read-only. To change `C`: run `node mako-matcher/scripts/topup.mjs cap <C>`, send the printed `setCap` and add it to the decision record; no deploy is needed: the next top-up uses it and the settler's counters use it from the next UTC day (§6.3). To refill the contract: send MON to it from the owner wallet. A "possible key theft" alert is a suspected theft: run the emergency revocation below.

**State the settler keeps.** The settler stores its one in-flight transaction hash and sender in Durable Object storage. On start with a different key, it waits for the old hash's receipt, or for the old key's on-chain nonce to pass it without it, **[r27]** or for the exchange to stop listing the old key as an operator, after which the old call can only revert and its orders go back to the book, before its first send (adversary pass on r27 draft 7, D2: a call logged but never broadcast left the wait with no end). The outcome is reported to the market Durable Object as for any send. **[r11]** A key change, planned or emergency, does not reset the daily cap counters: they are keyed by settler and UTC day (§6.3), so the old and new keys together stay within `C` and `K` that day. **[r12]** A rotation changes the secret only. It never changes the settler's binding, class or object id (§6.1), **[r13]** nor the Worker name or environment, and the deploy in rotation step 3 and emergency step 3 runs the release check (§10.3) before and after `wrangler deploy`. If it fails, the release has failed and the owner fixes or rolls it back before trading resumes. A settler whose identity does not match sends nothing in any case (§6.1). **[r15]** Withdrawn with the run-time id check (§6.1): such a settler can send, the wallet bounds it, and the reconciliation flags what it sends (§6.3). **[r13]** A rollback of `mako-matcher` (`wrangler rollback` or the dashboard) is itself a new deployment, so it runs the same release check before and after: before, on the configuration of the version rolled back to (its commit); after, on the deployed Worker. **[r26]** **[r27]** On a rollback, every configuration value that differs between the version rolled back to and the current checkout (`K`, `ε`, the funder address) is reported, not a failure: the helper and the release check's chain reads take every value from the current checkout, never from a deployed version, so a rollback cannot change what is checked, and the counters are not the bound. What fails a rollback as it fails a release is the chain fact: an operator transaction the reconciliation alerts on (§6.3 step 2). Between the rollback and the after check, the settler's run-time id check (§6.1) still refuses to send from a wrong object. **[r15]** Withdrawn: there is no run-time id check. In that window a wrong object can send; the wallet bounds it and the reconciliation flags it (§6.3). **[r14]** The rollback check is defence and alarm, not the bound: a rollback that restores a deleted key (adversary pass on r13) spends at most what the operator wallet holds (§6.3).

**[r14] A new settler identity.** Before a bootstrap (§6.1), delete the old `mako-matcher` Worker, in whichever Cloudflare account it runs, so two settlers do not contend for one key's nonce. This is housekeeping. The funding rule bounds spend whether or not it is done. **[r15]** A new identity also uses a new operator key (planned rotation, below). Its send log starts empty, so the old settler's transactions on the old key would show as unknown and stop top-ups; the new key's reconciliation starts at its first top-up, from nonce 0. **[r27]** So every listed key is retired first, while the old settler and its log still exist: `setOperator(k, false)` for each key that is an operator (rotation step 4, which ends the wait for a call in flight), run the helper on the current configuration and send each `retireKey` it prints (adversary pass on r27 draft 11, D1: in the middle of a rotation, retiring only the settler's current key left the rotation's old key listed, its honest sends only in the deleted Worker's log, and the theft alert stopped settlement); only then delete the old Worker and bootstrap the new identity, then give it its new key by rotation steps 1 and 2 and step 5's top-up (`setOperator(new, true)`, `addKey(new)`, a top-up), with the new secret pushed only to the new Worker, so the new key's first nonce is in the new settler's log; settlement waits through these steps (adversary pass on r27 draft 3, D2: a new key first used by the old Worker under rotation step 3 had nonces only in the old log). (Adversary pass on r27 draft 2, D1: retiring after the bootstrap read the old key's honest history against the new, empty log, raised the theft alert and failed the release check).

**Planned rotation.** **[r27]** Reordered so the old key is revoked before anything waits on the new one (adversary pass on r27 draft 9: step 3's check, a fill from the new key, came before the only steps that revoke and retire the old key, so a new key funded too little to send, or an old call that never mined, stopped the rotation for good). Settlement pauses from step 3, when the settler moves to the new key, unfunded (it holds and sends the wallet-short alert, which is expected here), until the new key's top-up in step 5, at most until the next UTC day.
1. Create the new key, save it in Bitwarden. Admin: `setOperator(new, true)`.
2. **[r14]** **[r27]** Owner: `addKey(new)` on the funder contract, once step 1 has mined, so a listed key is always one that is or was an operator. No top-up yet.
3. Push the new secret, then `wrangler deploy`.
4. Admin: `setOperator(old, false)`. This ends the settler's wait for the old key's call in flight (settler rule above): it lands, fails, or can only revert, and its charge is inside the allowance of §6.3. Orders in the book are unaffected, because no order names the operator.
5. **[r18]** **[r27]** Run the helper: it checks the old key, now not an operator, and prints `retireKey(old)` and no top-up; the owner sends it and notes it in the decision record (§6.3, retired keys). Once it mines, run the helper again: it prints the new key's top-up, `C` minus the new key's balance, that UTC day if none was made yet, else the next. Confirm settlement resumes (one fill from the new key in the events); a secret change alone has stopped a Worker's schedule before (`DONE.md`, watchdog, 2026-09-21).
6. Send the old key's leftover MON to the admin wallet, however many tries it takes, and delete the old Bitwarden item. **[r27]** A shortfall the sweep finds is not alerted (§6.3, what this bounds).

**[r27] One runbook at a time** (adversary pass on r27 draft 13: an identity change interrupted by an emergency, resumed where it stopped, read the emergency's new key against the new, empty log; an emergency started inside a contract replacement could not be executed; an identity change inside a lost-wallet replacement could not retire its keys). A runbook runs to its end before another starts, with one exception: a theft alert raised during any runbook starts the emergency at once, and the interrupted runbook then starts again from its step 1, on the state the emergency left. During a contract replacement, from its step 2 on, the emergency is only its steps 1, 2 and 7: replacement step 2 has already revoked every key, the old contract is not called again, and replacement step 5 gives the new key on the new contract. An identity change does not start while a replacement is under way.

**Emergency revocation (key suspected stolen).**
1. Admin: `setOperator(old, false)` at once. That one call ends every power of the stolen key. **[r27]** A revoked key is never made an operator again, even when the suspicion clears: it is retired and replaced. A `topUp` printed before this step is not sent; the helper is run again. If anything else is in doubt, also `setPaused(true)`; withdraw, merge, cancel and redeem keep working.
2. Any transaction from the old key mined after step 1 reverts and changes no state; **[r27]** it is still charged, at most `L` for the settler's one call in flight (§6.3, what this bounds). The settler sees "not operator", drops no order, stops and alerts (§6.2). Orders it was settling go back to the book; they stay valid signed orders. **[r4]** While the exchange is paused, the settler sees `Paused` and holds every market without dropping anything (§6.2).
3. **[r19]** **[r27]** First `retireKey(old)`, written off, noted in the decision record (§6.3, retired keys); until the old key is retired the helper refuses every top-up. **[r27]** Every other key that is an operator or listed (a planned rotation under way leaves two) is also revoked with `setOperator(k, false)` and retired as the helper prints it, rotated if clean, so the replacement below is the only listed key (adversary pass on r27 draft 10: an emergency in the middle of a rotation left the rotation's old key listed near `C`, and every later top-up too small to send). **[r4]** Rotation steps 1 to 3 with a new key (`setOperator(new, true)`, `addKey(new)`, the new secret and `wrangler deploy`), then the new key's top-up as in rotation step 5.
4. **[r4]** If step 1 paused the exchange: `setPaused(false)`, once nothing else is in doubt. The new key cannot settle before this, because a pause stops `matchOrders`.
5. **[r4]** Confirm settlement resumes: one fill from the new key in the events. This is the check of rotation step 5, which a paused exchange could not pass. That is why r3's order, with the check before the unpause, was withdrawn.
6. **[r4]** Rotation step 6 for the old key's leftover MON and its Bitwarden item. **[r14]** A stolen key's balance cannot be swept. It was funded under the daily rule, so it is inside the bound, and it is written off. **[r18]** **[r27]** Its `retireKey` takes it out of the reconciliation and the sum. **[r19]** That is done in step 3, before the new key's top-up; here only the Bitwarden item is deleted. The new key is funded as in rotation step 5.
7. List every fill sent by the old key from the suspected time to step 1 (the settlement transaction's sender), and publish the list on the affected market pages. Users who want to void their signed orders use "Cancel all on chain".

**[r31 d3] Strike review.** **[r31 d4]** Withdrawn with strikes (Q13). A stopped market is restarted by a person, as before.

**[r27] Funder contract or owner wallet replaced.** If `MakoFunder` must change, or the owner's wallet is lost or in doubt: 1. If the old owner wallet still works, `close` the old contract to the owner's new wallet at once; a checkout still pointing at it then gets `Closed`. A lost owner wallet cannot send a new call. **[r27]** A top-up it sent before, still pending, can mine only on the UTC day it names, never after the day the new contract is deployed (adversary pass on r27, D2), and a `close` queued behind it mines after it. 2. Admin: `setOperator(k, false)` for every operator key; settlement stops. **[r27]** Then run the helper on the current configuration, still the old contract: it reconciles every old key a last time, alerting on a theft, and prints each `retireKey`, sent if the old owner wallet still works (adversary pass on r27 draft 12, D1: nothing read the old keys after the last top-up run, so a theft before the replacement was never found; and a new key enabled at rotation step 1, not yet listed, stayed an operator). 3. Deploy a new `MakoFunder` from the owner's wallet, `setCap`, and deposit; its `lastDay` starts at the day of deployment, so its first top-up comes the next UTC day, after every day an old call could name. 4. Point the configuration source at it, add the dated decision-record entry, and deploy; the helper now reads only the new contract. 5. The next UTC day, rotation steps 1 to 3 for one new key on the new contract (`setOperator(new, true)`, `addKey`, the new secret and deploy), then its top-up as in rotation step 5; settlement resumes (adversary pass on r27 draft 10: draft 10 cited only steps 1 to 3, which no longer fund the key). 6. The old keys left with the old contract: they are not operators, nothing reads them, and their leftover MON, at most `C` with any call still in flight (at most `L` each, §6.3), is swept to the admin wallet; until then it sits outside the new contract's sum and cannot settle. **[r27]** The new contract lists only new keys, each from nonce 0 (adversary pass on r27 draft 2), and settlement waits from step 2 to step 5, a rare, disclosed pause (adversary pass on r27 draft 4: draft 4 ran the rotation before pointing the helper at the new contract, so no top-up could be printed and no old key retired). r22 to r26's funding wallet replacement runbook is withdrawn with the funding wallet.
